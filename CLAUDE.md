# Claude Code Instructions — Gym & Training Tracker

This file is read automatically at the start of every Claude Code session in this repo. Follow these constraints on every task unless explicitly told otherwise in a prompt.

## Hard constraints

1. **Vanilla HTML/CSS/JS only.** No frameworks (React, Vue, etc.), no build step, no npm dependencies for the deployed site itself. A Google Fonts CDN `<link>` is fine — that's already in use. The repo-root `package.json` and `/api` folder (added in Phase 3) are the one exception: they exist purely so Vercel can install and run the serverless function in `/api`. GitHub Pages ignores both — it never runs `npm install` and just serves whatever static files exist, so this doesn't affect the deployed site itself.
2. **No bundler, no TypeScript, no compile step.** GitHub Pages must be able to serve the files as-is.
3. **Data persists only via `localStorage`**, with exactly one deliberate exception: step counts. Everything else in this app — templates, logged sets, saved videos, timer state — must stay client-side only. Phase 3/3.5's `/api` functions exist only to hide an API key, not to store data. `api/log-steps.js` is the one real exception, and only because Apple's HealthKit has no public web API for a browser to read directly — see its "Current architecture" entry below before assuming this constraint is absolute.
4. **Match the existing design tokens** defined in `style.css`'s `:root` block — a "pilates studio" palette, v2 ("Bold Chocolate"): background `#F1E4CF` (deeper oat), card `#FFF9EE`, ink `#2A1B10` (near-black espresso), muted text `#7A6650`, primary accent `#A65C2E` (a more saturated terracotta-mocha), secondary/neutral accent `#9C9284` (deepened silver), complete/success accent `#D69573` (richer blush), hairline borders `#DFC9A6`. The bottom tab bar is its own dark chocolate ground (`--color-tabbar-bg: #241609`, colour-picked directly from `icon-512.png` so it matches the app icon) with its own inactive/active tones (`--color-tabbar-inactive: #9A8265`, `--color-tabbar-active: #E8B27A`) rather than reusing the light-mode ink/mocha pairing. Any hardcoded `rgba()` shadow/glow that echoes a token color (the `.card` shadow, the `.day-card.is-today` pulse, the checkbox "just-checked" pop) must be kept in sync with that token's RGB value — they're literals, not `var()` references, so a future palette change has to update them by hand too. Don't introduce new colors or fonts without being asked.
   - **Fonts**: headings and page titles use `--font-display` ("Marcellus", `font-weight: 400` — its only weight, and it has no italic face, so don't set `font-style: italic` on it). Body copy, labels, and buttons use `--font-body` ("Poppins", weights 300/400/500 only — nothing bolder is loaded, so don't reach for 600/700). `--font-mono` ("JetBrains Mono", weights 500/600) is unchanged from before and stays reserved for stat numbers and data read mid-workout — weights, sets, reps, the timer countdown, calendar/day-card labels — anywhere legibility of digits matters more than the display/body voice.
   - **Color semantics**: mocha (`--color-mocha`) is the one primary accent — active/selected tab, buttons, focus states, "today" highlights (on light surfaces only — the tab bar uses its own `--color-tabbar-active` instead, since mocha doesn't have enough contrast against the dark tab bar ground). Blush (`--color-blush`) is reserved for completion/success only — a finished day card, a checked exercise, the small checkmark badge — never used for plain selection or navigation (the one deliberate exception is the Dance exercise type, which reads visually distinct by using blush for its own checkbox/toggle state — see the Dance section below). Silver (`--color-silver`) is the neutral tone for secondary/inactive UI — secondary and small buttons, icon buttons, unselected toggle segments, the calendar's "day being viewed" highlight (as opposed to "day completed," which is blush) and greyed-out other-month dates.
   - **Checkboxes/toggles**: the exercise checklist checkbox (`.exercise-checkbox`) is a custom circle (`appearance: none`), not a native checkbox — mocha outline unchecked, solid blush fill when checked. Follow that same pattern (mocha outline → blush fill) for any future checked/complete-style toggle; don't reach for `accent-color` with the old green.
   - **Cards**: `.card` uses `var(--radius)` (14px) corners, a 1px `var(--color-hairline)` border, a soft warm-toned ambient shadow (built from the ink color, not black — a harsh dark shadow reads wrong against the oat/cream palette), and a subtle top-to-card-color gradient for dimension. `.day-card` (the week-trail carousel tiles) intentionally keeps its own flatter, hairline-only look — the shadow/gradient treatment is scoped to `.card` only. The one shadow exception on `.day-card` is still the small mocha glow on `.day-card.is-today`, which reinforces the border rather than adding card-style depth. The `--grain-texture` overlay (a small procedurally-generated PNG, embedded as a base64 data URI in `:root` — SVG `feTurbulence` was tried first but rendered with too little contrast to read at real page scale) is applied only to the page background via `body::before`, not to individual cards. It's tinted toward the *original* v1 ink color — a minor, deliberately-accepted mismatch since it's low-opacity noise, not a solid fill; regenerate it if the ink token ever moves again and the drift becomes visible.
5. **The project owner is a beginner developer**, using this project to learn. Prefer clear, commented code over compressed or clever code. When making a nontrivial change, add a short comment explaining *why*, not just what.
6. **The project owner does not use the terminal directly.** When asked to commit, push, or run git/GitHub commands, run them and then summarize what was done in plain language — don't assume familiarity with git terminology.

## Current architecture

- `index.html`, `log.html`, `timer.html`, `plan.html`, `templates.html`, `history.html`, `videos.html`, `suggest.html`, `import.html` — markup only, no inline logic. Every page shares the same bottom tab bar; when adding a new page, add its tab link to all the others too.
- `style.css` — all styling
- `script.js` — all application logic, shared across every page (each render function guards itself with `if (!container) return` for pages that don't have that element)
- `api/suggest-template.js` — the one exception to "vanilla, no backend": a small Vercel serverless function that calls the Claude API on the site's behalf. See the Phase 3 entry below and the comments in that file for the full why.
- `api/import-screenshot.js` — same exception, for Phase 3.5: a vision-capable call to Claude that reads a workout screenshot and extracts exercises.
- `api/log-steps.js` — a third exception, and the first one that isn't about hiding an API key: it's the *only* server-side data store in the whole project. Apple's HealthKit has no public web API, so a browser can never read Steph's step count directly — an iOS Shortcuts automation on her phone (triggered whenever she opens the Health app) POSTs today's count here, secret-protected via the `STEPS_WRITE_SECRET` env var (checked against an `X-Steps-Secret` header). GETs are public/unauthenticated (read-only, non-sensitive) and return the whole `{date: steps}` blob, stored as one JSON value under the Redis key `steps-log` in the same Upstash instance Phase 3's rate limiting already uses. `script.js`'s `STEPS_API_URL` constant must point at the same deployed Vercel function's URL as `SUGGEST_API_URL`/`IMPORT_API_URL`.
- `localStorage` keys: `templates`, `weeklyAssignments`, `trainingLog`, `savedVideos`, `timerState`, `activeTab`, `exerciseReferenceCache`, `wgerReferenceCache`

Exercises (inside templates, and inside logged entries) always carry a `type` field: `"strength"` (uses `sets`/`reps`/`weight`), `"cardio"` (uses `distance`/`duration`), or `"dance"` (uses `duration`/`songs`/`effort` on logged entries; templates also carry an optional `link` to a reference video, shown as a small "Watch" link). Always branch on `type` when touching exercise-related rendering or logging code — don't assume one shape fits all exercises.

Stats and streaks (`calculateStreak`, `calculateLast30DayStats`) are derived, not stored — they're recalculated from `trainingLog` on every render. Keep it this way; don't cache these values in `localStorage`, since that would create a second source of truth that can drift out of sync.

The "How do I do this?" exercise reference (`toggleExerciseReference` in `script.js`) tries three tiers in order, each cached in `localStorage` the same way (~1MB, fetched once then reused): free-exercise-db first (real photos, but strength-only — zero cardio/yoga/Pilates coverage), then wger.de (no photos, but has an actual Cardio category free-exercise-db lacks; still zero yoga/Pilates pose coverage — checked directly, no free dataset covers those), then a "Search YouTube for [name]" link as the final fallback so a lookup is never a dead end. `findExerciseReference`'s word-matching explicitly skips any database entry whose name normalizes to zero words (wger's community data has a few non-Latin/mistagged entries) — without that guard, `[].every()` is vacuously true and those entries silently match every query.

## Roadmap

- **Phase 1 — COMPLETE.** Weekly plan, templates, strength + cardio logging, calendar view, rest timer, stats/streaks.
- **Phase 2 — COMPLETE.** Save TikTok workout videos via TikTok's public oEmbed endpoint (`https://www.tiktok.com/oembed`, CORS-enabled, no key needed). Saved as `savedVideos` in `localStorage`; the embed itself is rebuilt from `videoId` on every render rather than storing TikTok's returned HTML, since that HTML embeds a signed thumbnail URL that expires.
- **Phase 3 — COMPLETE.** AI-generated template suggestions. `suggest.html` posts a short goal string to `api/suggest-template.js` (deployed separately on Vercel — GitHub Pages can't run server code), which calls the Claude API (`claude-opus-5`, structured JSON output via a Zod schema) and returns a draft template the user can review and save into `templates`. The Anthropic API key lives only in Vercel's environment variables, never in this repo or in client-side code. A daily request cap (`DAILY_LIMIT` in that file, currently 15) is enforced server-side via a small Upstash Redis counter, since this is the one feature in the app with a real per-use cost. `script.js`'s `SUGGEST_API_URL` constant must point at the deployed Vercel function's URL.
- **Phase 3.5 — COMPLETE.** Screenshot import. `import.html` lets Steph upload a screenshot of a workout app screen (e.g. Heather Robertson Fitness); the image is resized in the browser (`resizeImageForUpload` in `script.js`, capped at 1280px so it stays well under Vercel's ~4.5MB request body limit) and posted to `api/import-screenshot.js`, which reuses the same Phase 3 infrastructure — same Vercel deployment, same Anthropic key, same Upstash-backed daily cap pattern, just a separate `DAILY_LIMIT` counter (`imports:${today}`) so the two AI features don't share a budget. Claude reads the screenshot with vision and returns structured strength exercises (name/sets/reps/weight, weight converted to kg if shown in lbs); the user reviews and edits the extracted rows before saving them straight into `trainingLog` for a chosen date. `script.js`'s `IMPORT_API_URL` constant must point at the same deployed Vercel function's URL as `SUGGEST_API_URL`.
- **Phase 4 — COMPLETE.** Daily step count in Stats, including Steph's on-phone Shortcut setup (verified working end to end 2026-08-28). An iOS Shortcuts personal automation, triggered whenever Steph opens the Health app, reads today's step count and POSTs `{date, steps}` to `api/log-steps.js` with a shared-secret header (`X-Steps-Secret`, checked against the `STEPS_WRITE_SECRET` env var). The Home page GETs the stored `{date: steps}` log from the same endpoint (public, read-only) and shows a "steps (30d)" stat alongside the existing 30-day stats — see the "Current architecture" entry for `api/log-steps.js` above for the full why. This is the one feature in the app where the actual data pipeline lives partly outside this repo, on Steph's phone — if steps ever stop showing up, check the Shortcut is still enabled before assuming a code bug.

## Explicitly rejected approaches — do not attempt

- **Pulling data from Nike Run Club.** No public API exists. The only workarounds require manually extracted, unstable personal auth tokens and would breach Nike's terms of service. Do not suggest or implement this, even if asked to "find a workaround."
- **Strava API integration.** A legitimate option for the future, but treat it as out of scope unless the project owner explicitly opens it as a new, separate task.
- **Switching to a component framework (React, etc.) or a design system like shadcn/ui**, even for "just polishing the UI." This project intentionally uses a bespoke visual identity (calendar-page day cards, custom color tokens) — a framework switch was already considered and declined.
